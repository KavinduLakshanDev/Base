# Daily Log - 2026.07.10

## Bug Fixes: Batch Discount Logic

### The Problem
During sales transactions and on the product edit screen, certain stock batches (specifically those created through Goods Receipt Notes (GRN) or stock adjustments) were not applying the correct discounts. For example, batch `ADJ-VIS-VIS-0023` for item `00423` was showing a `0.00` discount instead of the `50.00` discount defined in the master item. 

### Root Cause Analysis
When specific batch price records (in the `item_price_det` table) or purchase records (in `purchase_det`) are created for things like stock adjustments, they often save discounts as a default `"0.0000"`. 

The PHP code responsible for applying discounts used a shorthand check (`?:` and `??`) to see if a batch had a specific discount. In PHP, the text string `"0.0000"` is treated as a valid, "not empty" value. Because of this, the code accepted the `"0.0000"` discount instead of falling back to the master item's discount.

### Resolutions Implemented

#### 1. Sales Screen Base Item Discount Leakage (`SalesController.php`)
- **Location:** `searchItems()` method
- **The Problem:** The base item's price detail was being fetched by simply ordering `item_price_det` by `ItemPriceKey desc` without filtering by batch. This caused the discount of the newest batch (e.g. `GRN-VIS-VIS-0171`) to be attached to the base item template, and incorrectly cascade to other batches (like `GRN-VIS-VIS-0049`) that had no specific discounts.
- **Change:** We added a fallback loop in `searchItems` to properly reset the `tiers` array for each batch if the purchase details didn't contain specific tier information. This stops discounts from bleeding across batches.

#### 2. Sales Screen Stock Adjustment Fallback (`SalesController.php`)
- **Location:** `searchItems()` method
- **Change:** We updated the logic that calculates batch pricing for the Sales screen. Instead of the standard `?:` fallback, we explicitly cast the discount and quantity to a `float` and use `empty()`. 
- **Impact:** If the batch-specific discount is actually `0` (e.g., `"0.0000"`), the system now recognizes it as empty and correctly falls back to the default discount stored in the `itemmaster` table.

#### 3. Product Edit Screen (`ProductController.php`)
- **Location:** `getPricesForBatch()` method
- **Change:** When the user selects a batch from the dropdown on the Product Edit page, the frontend calls this API to fetch the batch's specific pricing. We applied the exact same `empty((float)...)` fallback logic here.
- **Impact:** The "Retail Discounts" section will no longer populate with `0` when a batch has no special discount. It will accurately display the fallback discounts from the master item.

### Summary
The system now correctly isolates batch discounts (preventing leakage from newer batches to older ones) and differentiates between a batch having "no special discount" versus a batch intentionally having a zero discount, ensuring that standard item discounts are preserved across all inventory adjustments and sales screens.
